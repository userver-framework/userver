# Code review rules for userver

Apply these rules to reviews and self-review alongside the project's coding and
contribution requirements. Read outside the diff as needed, but report only issues
introduced by the change. Verify findings against code, tests, and documentation;
do not report speculation or repeat an existing discussion without a new regression.

For each finding, identify the defect, provide concrete evidence, explain
the consequence, and ask the author to address it. Leave implementation choices
to the author; do not provide replacement code, documentation, or patches unless
requested.

For documentation changes, check sources and links. Inspect rendered pages or
build artifacts only if already available; do not start a local documentation
build solely for this checklist. Do not report a rendering-dependent finding as
verified without rendered output.

Before reviewing a changed file, read its opening comment block, even if absent
from the diff; for deleted files, read the previous revision. Skip findings on
output identified by its header as generated, and review changed schemas,
generators, and templates instead. Recognize banners such as:

- `THIS FILE IS AUTOGENERATED, DON'T EDIT!`;
- `THIS FILE IS AUTOGENERATED, DO NOT EDIT !!!`;
- `This file is generated from ...` followed by `DO NOT EDIT!`.

Allow variations in case, whitespace, and comment syntax without requiring
`AUTOGENERATED`.
Templates such as `.jinja` remain in scope even if they contain a future output
banner; ordinary references to generation do not make a file generated.

## 1. Preserve the public API

Check backward compatibility even when there are no callers in this repository.
Public headers live under `*/include/userver/` and are included as `<userver/...>`;
`impl` and `detail` are internal.
Use documentation to identify other user-facing interfaces. Compare old and new
contracts for:

- removed or renamed headers, types, and functions;
- signatures, return types, defaults, template constraints, and extension points;
- overloads that make existing calls ambiguous or required interface methods that
  break user implementations;
- documented lifetime, ownership, errors, results, and configuration, including defaults.

A private implementation change alone is not an API violation. For each finding,
show a previously valid call, interface implementation, or configuration that
breaks, and explain why. Request restored compatibility or, for intentional
breakage, a migration guide identifying the affected API and user migration steps.
Do not choose the new API or design compatibility wrappers for the author.
Respect migrations documented in the change description and the deprecation
policy; do not require preservation beyond that policy or assume ABI guarantees
without evidence.

## 2. Reuse existing utils functions

Avoid duplicating logic. For added or changed helpers and repeated logic, look for
suitable public `userver::utils` functions in `universal/include/userver/utils/`,
`core/include/userver/utils/`, then the module's dependencies. Read candidates'
declarations, implementations, and tests; similar names do not imply equivalence.

Suggest reuse only when it preserves semantics and simplifies code. Check
missing-value and error handling, constness, ownership, lifetime, copies,
allocations, complexity, and module availability. Do not add a higher-layer
dependency solely for reuse or suggest deprecated, `impl`, or `detail` entities.
Name the function and public include header and explain why they fit. Do not
report unsuitable alternatives or request changes to unchanged code outside the diff.

## 3. Keep documentation complete and examples verifiable

Keep documentation concise and easy to understand; use `@brief` where possible.

Check that each new public method, including overloads, documents its contract,
and each added or changed enum value documents its meaning. Update documentation
when contracts change. Read declarations, implementations, tests, and documentation
before reporting gaps. Accept inherited documentation or working Doxygen references
that fully cover the contract instead of requiring duplicate prose.

In added or changed Doxygen prose, reference userver entities with fully qualified
`@ref` targets, including namespaces, and verify that they resolve correctly.
Exclude identifiers in code examples and literal configuration values. In
self-referential headings such as a component's "Static options", use the fully
qualified type name as plain text to avoid Doxygen recursion warnings.

Do not use `@code` blocks. Code examples must use `@snippet` from code built and
exercised by tests; verify the file and markers. Explicitly labeled illustrative
output and pseudocode are not executable API examples.

Identify the undocumented contract, missing or incorrect reference, or untested
example, and explain the unclear behavior, missing API navigation, or risk of
example drift that the author should address.

## 4. Make ownership clear and avoid unnecessary copies

Use values or `std::unique_ptr` for owned objects, and `std::shared_ptr` only when
shared ownership is required. For every added `std::shared_ptr`, verify that more than
one owner must extend the object's lifetime; otherwise request a value or
`std::unique_ptr`. For borrowed objects, use references when their lifetime is guaranteed.

For clients provided by component dependencies, a reference is usually sufficient,
including as a member: the component system guarantees that these clients outlive
the component using them. See
@ref clients_from_components_lifetime "References from components and lifetime of clients".

At copy-producing ownership transfers in added or changed code, check whether
moving at the source's last use avoids a nontrivial copy without changing behavior.
Inspect the type, constness, selected overload, and callee's ownership contract;
an lvalue alone does not prove a copy.

Verify that the source is no longer needed on all affected paths, including
aliases, captures, cleanup, and exception handling. Do not suggest moving borrowed
values, values still needed by their owner, scalars, const sources that would
still be copied, or arguments to borrowing calls. Do not wrap returned locals in
`std::move` when that prevents copy elision. Identify the actual copy and explain
why the final use can transfer ownership without changing the contract.

## 5. Keep public headers minimal and self-contained

Check whether implementation details in public headers can move to `src/`,
including those in `impl` or `detail` namespaces. Keep definitions visible only
when required by templates, `constexpr` evaluation, inline behavior, or type
completeness.

Prefer @ref utils::FastPimpl when hiding implementation details.

Check affected includes against declarations, inline definitions, templates,
macros, and complete-type requirements. Include direct dependencies; never rely
on transitive includes. Dependencies needed only out of line belong in the source.
Respect intentional, documented umbrella headers; preserve the public API and behavior.

Name each unnecessary exposed detail or include, explain its added dependency
or exposure and why consumers do not need it, and request extraction to `src/`
or removal while preserving a self-contained header.

## 6. Follow the PR style guide

Check the title and description against the conventions below, distinguishing
requirements from recommendations. Do not report personal wording preferences.
Explain a violation's consequence for reviewers or public release notes.

@anchor pr-titles-and-descriptions
### PR titles and descriptions

Write titles and descriptions in English for public readers and release notes.
Use public issue links for context; omit private identifiers, private links, and
organization-specific tooling details, and do not request them in review.

#### Title

Use `type component: message`. Prefer at most 72 characters for readable GitHub
listings; clarity takes precedence over this recommendation.

| Type | Use for |
| ---- | ------- |
| `bug` | Fixing a noticeable bug. |
| `fix` | Fixing a bug. |
| `feat` | Adding functionality or tests. |
| `refactor` | Substantially changing code without adding functionality. |
| `typo` | Trivial typos or minor corrections that do not belong in release notes. |
| `cc` | Coding conventions, comments, or documentation. |

Choose the component primarily affected:

- a public include directory, such as `logging`, `cache`, `tracing`, or `engine`;
- `statistics` for `utils/statistics`;
- `core` for changes spanning several directories in `core`;
- a driver, such as `postgres`, `mongo`, or `redis`;
- `scripts`, `cmake`, or `docs` for those areas;
- `userver` for changes spanning several categories.

Describe the PR's result in the imperative (`fix`, `add`, `remove`, not `fixes`,
`added`, `removed`), completing "If applied, this change would ...".

Bad: `logging: fixed message formatting` omits the change type and uses a
past-tense message.

Good: `fix logging: correct message formatting` identifies the change type
and component and describes the change in the imperative.

#### Description

Explain the problem and resulting behavior; a linked public issue that fully
explains the change can replace the description. Separate the description from
the title, and optional trailers from the description, with blank lines.

Prefer public issue links and a normal validation paragraph over `Relates:` and
`Tests:` trailers; neither trailer is required. Describe the validation actually
performed and any material limitations.

## 7. Check algorithmic complexity

Determine time and space complexity of added or changed algorithms, stating what
the input sizes represent. Include work in callees and container operations,
repeated searches, copies, and allocations. Nested loops alone do not prove
quadratic complexity; check total work.

For `O(N * N)` time or worse, suggest an improvement or explicitly request one.
Verify that alternatives preserve behavior and account for their memory cost.
If input bounds or requirements prevent improvement, explain the constraint
instead of claiming an unsuitable alternative is equivalent. For example, an
index replacing repeated searches must preserve duplicate handling and ordering.

## 8. Extract template-independent implementation

For large template classes, identify state and methods independent of template
parameters. Where behavior is preserved, extract them into a non-template `impl`
class stored as a member of the original class, with method definitions in a
`.cpp` file to avoid repeated parsing and instantiation by consumers.

Check ownership, lifetime, layout requirements, and dependencies. Keep definitions
visible when required by template instantiation or `constexpr` evaluation, and
preserve the public API and semantics. Identify the state or methods that can be
extracted and explain why they can move out of the header.

## 9. Prefer meaningful enums to bool parameters

Avoid `bool` function parameters where possible: boolean arguments make call sites
hard to read because their meaning is hidden in the function declaration.
Use enums with meaningful values instead. As an illustrative example, replace
`Call(true, false)` with `Call(kHighPriority, kReadOnly)`, where `kHighPriority`
and `kReadOnly` are enum values describing the requested behavior.

## 10. Write clear and defensive code

Use modern C++20 and established project practices. Make contracts explicit and
use defensive checks. Check invariants with @ref UASSERT and @ref UASSERT_MSG
from `<userver/utils/assert.hpp>`. Configuration errors must be informative and
include hints on how to fix them where possible. Avoid no-op code, which can be misleading.

Keep code simple and self-explanatory: use clear names and small, focused functions.
Replace magic numbers and strings with named `constexpr` constants or equivalents.
Do not add comments to production code; express behavior through code instead.
In tests, add comments only when names and code structure cannot convey the behavior.

## 11. Cover new behavior and bug fixes with tests

New functionality and bug fixes must have tests. Add or update relevant documentation.
For flaky failures caused by production code rather than the test itself, first
add a test that reliably reproduces the bug without flakiness, then fix the code.

Keep the test set minimal. A bug fix needs one test that fails without the fix;
add another test only if it covers a distinct behavior of the change that no other
new or existing test exercises. When reviewing, request removal of tests that:
- repeat the same code path with a different API flavor (sync/async, unary/streaming,
  retry/no retry) unless the change affects that flavor specifically;
- check scenarios that are practically unreachable or need artificial setup
  that does not occur in real usage;
- duplicate assertions of existing tests.

## 12. Use userver synchronization and I/O primitives

Do not use C++ standard library or libc synchronization or blocking I/O on the
main task processor. Use userver primitives instead; see
@ref scripts/docs/en/userver/intro.md and @ref scripts/docs/en/userver/synchronization.md.

## 13. Keep production changes focused

Check whether the production-code diff can be reduced without
compromising functionality, performance, or readability. Exclude tests and
documentation from this check.

## 14. Use fmt for formatting

Use the `fmt` library for formatting instead of `std::format` and similar APIs.
Build strings with `fmt::format` rather than chains of `operator+`, `std::to_string`,
or `std::ostringstream`.
